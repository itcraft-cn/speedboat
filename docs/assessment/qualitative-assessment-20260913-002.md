## 二、领域识别

**关键词**：Raft、选举、心跳、任期、共识、分布式锁、跨机房。

**定性：基础设施组件**（分布式协调/中间件），不是业务系统。
基础设施级"允许宽松度：极低"——要求高可用、强一致、可扩展，且**必须假设网络对端不可信**。

## 四、尖锐总结（300-500 字）

Speedboat 是一个**骨架矫健、内脏偏软**的分布式主节点选举组件：架构分层与策略抽象达到开源库水准，Raft 主路径经三轮修复后算法语义基本自洽，这在前四步的数据上有明确支撑（重复度 1.76%、设计分 6.5）。但把它放到"基础设施"的天平上，两个地基问题决定它当前只能处于"演示可用"，而非"生产可用"。

第一，**身份系统形同虚设**。节点 ID 带随机后缀且 peer 侧用另一套 "peer-" 规则生成，同一节点在不同进程里有两个名字。Raft 的一切安全属性——同一任期一票、成员唯一性、故障记录追踪——都建立在"ID 唯一且稳定"上，这个前提在本项目不成立。这不是 bug，是地基混凝土没浇好。

第二，**	write 内存即真理**。term/votedFor/日志全部驻留内存，快照与恢复是空方法。进程重启瞬间"忘记"自己投过谁的票、自己在哪个任期——Raft 分区恢复期最危险的时刻，恰恰是它最失明的时刻。任何一个教程级 Raft 实现都会写先写 WAL，本项目没有。

第三，**零认证通道**。任何能撕到端口的主机可伪造投票/日志请求灌输集群，唯一的防线是 term 竞争的对等博弈——也就是说协议本身要求可信网络，而它从未声明过这个假设。

开发能力良好（策略插拔、修复节奏快、测试习惯养成），运维与安全是空白。领域匹配度：**部分匹配**——作为集群内私网、受控环境的实验组件合格；作为对外服务的基础设施不合格。改造次序：身份稳定化 → 持久化 → 认证，全都不需要动 Raft 主算法，属于"地基工程"而非"结构手术"，3-5 人日可达生产底线。
