# Speedboat 项目问题侦测报告（2026-09-13）

> 输入：code-deconstruct（docs/destruct/，已更新至 2026-09 代码）、code-review（code-review-20260913-001-java.md）、code-detect-dup（dup-20260913-001/002）。
> 原则：理性、客观、实际、真实，不恭维。

## 一、五维度评分

### 1. 设计质量（权重 30%）—— 6.5 分

**加分项**：
- 分层清晰：facade(config/lock) / raft / transport / strategy 四层，包间无循环依赖
- 策略模式用得彻底：VoteWeightStrategy / GroupStrategy / HealthCheckStrategy / RegistryStrategy / ChangeValidationStrategy 均接口化，可插拔
- 状态机转移用 NodeState 枚举 + canTransitionTo 白名单，防非法转移
- 帧协议 length+crc+类型字节设计简洁自洽

**减分项**：
- **节点身份体系设计缺陷**（nodeId 随机后缀 + "peer-" 前缀双轨）——这是贯穿全系统的地基问题，本应得 8 分，直接拉低
- RaftNode 1252 行上帝类（选举+日志复制+成员变更+锁无关职责混合）
- 成员变更双实现并存（RaftNode 内嵌 + MembershipCoordinator），职责重叠
- `RaftGroup`/跨机房级联模式半成品（Speedboat 跨机房模式未接 voteWeightStrategy、RaftGroup.getGroup 死代码）
- 无持久化设计（快照/restore 全空实现），设计文档标注了接口但架构未闭环

### 2. 性能质量（权重 25%）—— 6.0 分

**加分项**：懒连接自愈、NIO 双 EventLoopGroup、COW 列表适合读多写少、超时统一从 pendingRequests 移除。

**减分项**：
- 心跳日志洪水：50ms 间隔 × 每 peer 3 条 INFO（P1-4）
- `handleAppendEntries` 全量 COW 重建日志，O(n) 复制放大
- `logger.info` 热循环打对象（DistributedLockImpl.tryLock 每个 attempt 2 条 info）
- `getEntryAt` 线性扫描 O(n)，按 index 无二分（日志量大时 Leader 扫描退化）
- Netty server pipeline 未注册 decoder 顺序问题已修，但 maxFrame 1024 过小造成隐性重连瓶颈（P1-5）

### 3. 安全质量（权重 20%）—— 4.5 分

**加分项**：CRC 帧校验、无硬编码密钥、无反序列化白名单外的类型注入（CustomSerializer 固定注册表）。

**减分项**：
- **传输层零认证**：任意能连通端口的进程可伪造成节点发 RequestVote/AppendEntries，term 竞争是唯一防线。对"竞选主节点"这种高权限组件不可接受（延续 2026-07 结论，仍未修复）
- Protostuff 反序列化无大小前置校验（依赖 1KB 解码器兜底）
- 日志可能泄漏 nodeId/peer 拓扑（低风险）

### 4. 代码质量（权重 15%）—— 6.5 分

**加分项**：类头注释覆盖率高（2026-08 JavaDoc 专项），Builder 模式规范，异常均有日志，无 while(true) 死循环（配置解析的 break 可控）。

**减分项**：
- P0-1 锁续期 executor shutdown 复用 bug
- 违例：Executors 工厂 4 处、System.out/err 19 处（ClusterTestRunner）、`new DoubleCheckedLocking` 不适用、COW 重建
- 空实现占位（getGroup 返回 null、snapshot/restore 空方法）
- 37 个测试文件/61 主文件，测试户数比 0.6，核心算法（RaftNode）测试覆盖充分但 lock 層集成窄

### 5. 重复度（权重 10%）—— 9.0 分

- jscpd：1.76%，simian 阈值10 仅 62 行重复 / 6550 行
- 但重复高度聚集在三处"结构性重复"：Speedboat 单机房/跨机房启动 90% 相同（14 行）、两个 GroupStrategy 29 行、两个 RpcHandler 21 行——应通过抽象基类消除，是质量风险而非数量风险

## 三、重构方案（上策/中策/下策）

### 上策：身份与安全重构（4 阶段，预计 3-5 人日）

1. **节点身份稳定化**（最高优先）
   - `generateNodeId(hostname, ip)` 去掉随机后缀；peer 与自身同一生成函数
   - 冲突检测：start 时发现重复 nodeId 再打散（现有 random 仅作 fallback）
   - 测试：三节点真实网络测试改为主节点断言 leaderId 全一致

2. **传输层认证**
   - Pipeline 增加握手 handler：连接建立后首包交换 preshared token（可配置 `cluster.auth.token`），校验失败关闭通道
   - 帧协议扩展 authType 字节或独立握手帧均可，推荐独立握手帧避免动 CustomSerializer 帧结构

3. **term/votedFor 持久化**
   - 每次变更前同步写小文件（fsync），启动时恢复；MVP 不做日志 WAL
   - `LockStateMachine.restore` 顺带实现锁表快照（可选）

4. **结构性清理**
   - RaftNode 拆出 `MembershipProposer`（成员变更 250 行独立）
   - Speedboat 抽 `ClusterBootstrap` 消除单/跨机房重复
   - 删除死代码：RaftNode.checkMembershipChanges/getGroup/CalculateVotesNeeded

### 中策：仅做 P0 + P1-1/P1-5（1-2 人日）
锁 executor 修复 + nodeId 确定性 + 帧上限可配置化。安全认证与持久化延后。

### 下策：仅修 P0（0.5 人日）
仅修锁续期 executor bug，作为 hotfix。
