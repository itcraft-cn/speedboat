## 1. 背景

六台真实主机（主机房 192.168.193.174/175/176、备机房 192.168.193.51/53/55）以官方门面
`Speedboat.start(PropertiesConfigProvider)` 跑通了四个故障场景，33/33 断言通过。

但运行期证据揭示了一个必须正视的架构事实：

> **当前"跨机房级联"实际上是两个互不相识的独立 Raft 组。**
> 基线状态即存在 2 个 `isMain=true` 的节点；任一机房被杀，另一机房的 Leader 与 term
> 完全不变——不是"跨机房容错生效"，而是两房本来就毫无关联。

四个场景"通过"的**真实原因**是两房各自独立成组。因此：

| 业务诉求 | 当前实现 |
|---|---|
| 主机房优先 + 备机房独立存活 | ✅ 满足（巧合地满足，因为两组各自独立） |
| 单个集群跨两机房、机房级故障仍有多数派 | ❌ **不满足** |
| 全局唯一 Leader（跨机房互斥） | ❌ **不满足** |

本文档的目标是**把级联真正实现出来**，使后两项成立。

## 2. 现状事实（代码核查）

| 维度 | 现状 | 影响 |
|---|---|---|
| 跨机房建组 | `doStartCrossDatacenterMode` 只取 `allNodes.get(datacenterIndex)`，peer 列表仅含本机房节点 | 父组无从谈起 |
| `RaftGroup` | 单进程模拟类（组内多 `RaftNode` 共享进程、无 transport 参数），门面**从不使用**；`RaftNodeImpl.getGroup()` 硬编码返回 `null` | 级联脚手架是死代码 |
| `notifyParentLeaderElected` | no-op，仅打日志 | 父子组联动未接线 |
| `election.cross.timeout.min/max` | `PropertiesConfigProvider` 已解析（默认 3000/5000），门面**未接入** | 父组超时无来源 |
| `voteWeightStrategy` | 单机房模式传入，跨机房模式**漏传** | 机房权重完全不生效 |
| `RaftNode.Builder` | 已有 `.datacenter()` / `.groupStrategy()` 方法，门面**未调用** | 能力闲置 |
| RPC 协议 | `RequestVoteRequest` **无 `datacenter` 字段** | 对端无法判断候选者机房归属 |
| 权重计算 | `QuorumCalculator.calculateVoteWeight` 传入的是**本地** `ctx.datacenter`，而非请求方机房 | `DatacenterVoteWeightStrategy` 恒判"同机房"，恒 +2，**语义错误** |
| `NettyTransport` | 构造期绑定单端口 + 固定 peer 列表，无动态增删、无分区（partition）原语 | 无法表达"对侧失联" |
| `isMain` | `raftNode.isLeader()` | 每个机房各出一个 `isMain=true` |

**结论**：级联不是一个"没接线的小缺口"，而是**协议层、成员层、仲裁层三层都缺失**。

## 3. 目标口径（既有设计文档）

### 3.1 双层级结构

```
┌─────────────────────────────────────────────────────────┐
│ 父组（跨机房层）：成员 = 各机房的子组 Leader（代表）      │
│ - 选举超时：election.cross.timeout（3000-5000ms）        │
│ - 心跳：跨机房心跳（设计稿 200ms）                       │
│ - 职责：选出【全局唯一 Leader】                          │
└─────────────────────────────────────────────────────────┘
                          ↑ 代表席位
┌─────────────────────────────────────────────────────────┐
│ 子组（机房内层）：本机房 3 节点                          │
│ - 选举超时：election.intra.timeout（150-300ms）          │
│ - 心跳：50ms                                            │
│ - 职责：选出【机房代表】，处理机房内高可用                │
└─────────────────────────────────────────────────────────┘
```

### 3.2 席位与权重规则（设计稿原文口径）

- 子组**先**选出 Leader，子组 Leader **参与**父组选举。
- 权重 = 基础 1 + 机房权重：
  - 同机房：**+1 提权**
  - 异地机房：**-1 降权**
  - **本机房故障时：降为 0**（故障机房被摘出权重分母）
- 超时分层：父组超时必须**显著长于**子组超时，保证子组先收敛、父组后收敛。

### 3.3 产出语义

- 机房内 Leader 处理本地请求；
- **全局 Leader 处理跨机房请求**；
- **全局 `isMain=true` 在整个六节点拓扑上唯一**——这是本次实现的核心价值。

## 4. 三条硬约束

这三条约束决定了方案的可行性边界，**必须先决策再实现**。

### 约束一：两机房父组只有 2 个投票成员

设计稿的示例拓扑是**三机房**（北京/上海/深圳），父组 `majority(3) = 2`，天然容 1 机房故障。

本项目拓扑是 **2 机房**，父组投票成员 = 2：

- 标准 Raft `majority(2) = 2` → **任一机房失联，父组即失去多数，永远选不出全局 Leader**；
- 但场景②④要求"杀光一个机房，另一个机房仍能选出主"。

> **结论：父组不能使用标准 Raft 静态多数派。**
> 必须引入 **失联成员降权（degraded quorum）**：对侧代表超过 `election.cross.timeout`
> 持续未响应 → 将其从父组权重分母中摘除 → 存活方按剩余权重重新计算多数。

这正是设计稿"本机房故障时：权重降为 0"的语义，但它**偏离了标准 Raft 的安全性保证**
（标准 Raft 中分母固定，死一个成员仍需多数，正是为了防脑裂）。

### 约束二：两机房没有第三故障域 —— CAP 决策点

降权的判定依据是"对侧失联"。若两机房之间是**网络分区**（双方进程都活着、机房内子组都正常）：

```
主机房侧：判定对侧失联 → 摘除备机房代表 → required=2，自身权重 2 → 当选 ✅
备机房侧：判定对侧失联 → 摘除主机房代表 → required=1，自身权重 1 → 当选 ✅
⇒ 双主（脑裂）
```

**根治办法是引入第三个故障域的仲裁者（witness / tiebreaker）**，`majority(3) = 2` 时，
分区只有一方能连上 witness，因此只有一方能成主。

但本环境**只有 2 个机房**：witness 放主机房则随主机房一起死（场景②失败），
放备机房则随备机房一起死（场景④失败），**对"机房级故障存活"毫无帮助**。

> **这是 CAP 的直接体现，无法靠实现技巧绕过，必须由业务决策：**
>
> - **选 AP（可用性优先）**：接受"两机房网络分区时可能短暂双主"，通过降级超时 +
>   epoch 大步跃升 + 对侧恢复后退让来**缩小**窗口，但不能消除。业务侧需 fencing。
> - **选 CP（一致性优先）**：要求提供**第三个故障域**部署 witness，否则必须接受
>   "杀光一个机房后无主"（即放弃场景②④）。

> ✅ **决策结论（详见 §7 决策二 / §8.3 / §8.5）：选 CP，并以「不对称权重」实现，
> 彻底移除降级机制。** 唯一性由权重数学保证，场景②退化为"无主"，
> 由 §8.6 的人工升级 API 提供运维兜底。本环境无第三故障域，故不引入 witness。

### 约束三：协议层缺口（所有方案的共同前提）

跨机房投票必须让对端知道"候选者属于哪个机房"，否则权重公式完全失效。
当前 `calculateVoteWeight` 传入的是本地 `ctx.datacenter`，**恒判同机房、恒 +2**，是确定性缺陷。

> **无论选哪一策，`RequestVoteRequest` / `PreVoteRequest` 必须扩展 `datacenter` 字段，
> 且接收侧必须使用请求方携带的机房标识参与权重计算。**

## 5. 公共前提改造（三策共同，可先行落地）

这四项与父组选型无关，是任何级联方案的必要条件，建议**作为第一批独立提交**：

| # | 改造项 | 说明 |
|---|---|---|
| P1 | RPC 协议扩展 `datacenter` | `RequestVoteRequest`、`PreVoteRequest` 增加机房标识字段；接收侧改用**请求方**机房参与权重计算 |
| P2 | 跨机房模式补传 `voteWeightStrategy` | 消除当前漏传，使 `DatacenterVoteWeightStrategy` / `PreferNodeVoteWeightStrategy` 真正生效 |
| P3 | 接入 `election.cross.timeout.min/max` | 门面读取并用于父组（或父组仲裁）超时 |
| P4 | 机房标识语义修正 | `resolveDatacenterId` 当前在 `datacenter=` 配置后会让两机房拿到**同一个** ID；需改为按 `datacenterIndex` 区分（如 `datacenter=dc-0` / `dc-1`，或索引派生） |

**附带缺陷（建议一并修）**：`RaftNodeImpl.getGroup()` 返回 `null` 属死代码，
`notifyParentLeaderElected` 是 no-op 桩——应随本次改造一并补实或明确删除，避免继续误导。

## 6. 三策

### 6.1 上策 A：双层级联 + 父组「代表仲裁层」（复用端口，父组无日志）

> **推荐。** 保留完整双层语义，但承认"两机房父组本质上是一个仲裁问题而非共识问题"，
> 用与问题形状匹配的机制解决。

#### 结构

- **子组**：完全复用现有 Raft 逻辑（补 P2/P3 即可），端口 21001，peer = 本机房 2 节点。
- **父组**：新增**代表仲裁组件**，复用同一条 Netty transport 与同一端口，
  通过新增的一组跨机房 RPC（租约心跳 + epoch）与对侧机房代表互探。
- **父组不复制日志**：没有 `AppendEntries`、没有状态机、没有 checkpoint，
  只有心跳与单调 epoch——这与本组件"极简选主"的定位一致。

#### 席位规则（伪代码）

```
当子组状态从 FOLLOWER/CANDIDATE 变为 LEADER 时：
    本进程注册为【本机房代表】
    启动父组仲裁（以 election.cross.timeout 为周期向对侧机房全部节点发送代表探测）

当子组从 LEADER 退位时：
    本进程注销代表席位
    停止父组仲裁；若本进程当前持有全局 Leader，需先释放全局席位

父组探测广播到【对侧机房全部节点】，只有对侧的【子组 Leader】会以代表身份应答
    → 天然解决"对侧代表是谁"的发现问题，无需额外的服务发现
```

#### 全局 Leader 判定（伪代码）

```
全局 isMain = 本进程是子组 Leader  AND  本机房代表在父组仲裁中胜出

仲裁胜出条件（按优先级）：
  1. 对侧代表可达：
        机房优先级高者胜（主机房 > 备机房）→ 主机房代表为全局 Leader
  2. 对侧代表失联持续超过 election.cross.timeout.max：
        本机房代表【降级接管】，epoch 大步跃升
  3. 对侧恢复：
        取双方 epoch 较大者为准；epoch 低的一方立即退让为非全局
        → 避免"刚恢复就抢回"造成全局 Leader 抖动
```

#### 为什么能同时满足四个场景

| 场景 | 子组行为 | 父组仲裁行为 | 结果 |
|---|---|---|---|
| ① 杀主节点（主机房子组 Leader） | 主机房子组内快速重选（150-300ms） | 新 Leader 接替代表席位；若新代表机房优先级仍高，全局席位平滑移交 | 全局唯一 Leader 不变 |
| ② 杀光主机房 | 主机房子组全灭 | 备机房代表对侧失联超时 → **降级接管**，epoch 跃升 | 备机房成全局 Leader ✅ |
| ③ 主机房重启恢复 | 主机房子组重新选出 Leader | 备机房 epoch 更高 → 主机房代表先同步 epoch，再按优先级竞争 | 无抖动、无脑裂残留 ✅ |
| ④ 杀光备机房 | 备机房子组全灭 | 主机房代表失联超时 → 降级接管（其机房优先级本就更高） | 主机房成全局 Leader ✅ |

#### 优点

- **真正实现级联语义**："子组 Leader → 父组代表 → 全局唯一 Leader"，与设计稿一致；
- **零部署变更**：复用 21001，无需开新端口、改防火墙；
- **无父组日志复制开销**：不引入第二套 Raft 状态机与存储；
- **改动面收敛**：集中在"新增一个仲裁组件 + 一组 RPC"，**不动子组核心选举逻辑**（532 个既有测试可平滑保持）；
- **正确性易推理**：epoch 单调 + 优先级比较，比"在 2 节点上跑 Raft 并做降级"更容易证明；
- **可观测性好**：父组状态独立可打点（代表席位 / 仲裁状态 / epoch / 降级次数）。

#### 缺点与风险

- 父组**不是真 Raft**，与设计稿"跨机房层 Raft"字面不符 → **需同步修订设计文档措辞**；
- 分区双主风险依旧存在（约束二）；
- 仲裁规则是自定义协议，需要比"复用久经考验的选举路径"更充分的故障注入测试；
- 子组 Leader 切换与父组席位交接存在**短暂重叠窗口**，需设计"旧代表主动让位"协议。

#### 非功能性

| 维度 | 评估 |
|---|---|
| 可用性 | 高：满足全部四场景；机房级故障切换耗时 ≈ cross timeout（3-5s） |
| 一致性 | 中：分区时可能双主，需业务侧 fencing 或引入 witness 升级为 CP |
| 性能 | 优：父组无日志复制，跨机房流量仅为低频心跳（每机房 1 条，非 3 条） |
| 可扩展性 | 中：2 机房最优；扩到 ≥3 机房需把仲裁升级为多代表优先级/多数派 |
| 可观测性 | 优：父组状态可独立暴露 |

### 6.2 中策 B：双层级联 + 父组「真 Raft」（独立端口）

> **最正统的字面实现**：父子组都是完整的 Raft，故障域完全隔离。

#### 结构

每个进程运行 **两套** RaftNode + 两套 NettyTransport：

```
进程内
├── 子组：端口 21001，peer = 本机房 2 节点，intra 超时（150-300ms）
└── 父组：端口 22001（= 子组 21001 + cross.port.offset 1000），
    peer = 全部机房全部进程的 22001（全网互联，自身除外），
    cross 超时（3000-5000ms）
```

> **父组为何是全网互联而非只连对侧**：父组成员是各机房的"子组 Leader"，对侧代表运行期
> 才确定，故必须铺满对侧全部节点；但若同时跳过本机房，本机房的**非代表进程**就收不到
> 任何父组心跳（机房内没有别的进程会向它发），导致：①`parentLeader`/`parentTerm` 在全网
> 永不一致（非代表恒为 `none`/`0`），无法用"全网是否一致"判断父组收敛；②本机房换主后
> 新代表的父组 term 停在 0，只能逐轮选举一格格爬升追上当前任期，席位交接不平滑。
>
> 本机房的非代表进程因此成为事实上的 **Raft learner**（只跟随、不投票），
> 三重闸门保证它不会污染选举：席位门控（不竞选/不投票/不授预票）、
> 分母按机房去重（同机房 peer 权重恒不计入）、只接收复制。

#### 关键规则

- **席位**：本进程仅当 `子组.isLeader()` 时，父组节点进入**活动态**（竞选/投票）；
  否则**被动**（不竞选、不投票，收到父组投票请求回绝——因为本机房代表会响应）。
- **广播覆盖**：父组 `RequestVote` 向对侧机房**全部 3 个节点**广播，
  只有对侧子组 Leader 会以活动态响应，同样解决"对侧代表是谁"的发现。
- **isMain** = `子组 Leader && 父组 Leader`。
- **父组权重**：主机房代表 2 / 备机房代表 1（`DatacenterVoteWeightStrategy`）。
- **父组无状态机**：`stateMachine` 用 no-op，日志上限极小。
- **降级**：父组**仍需**失联降权机制才能满足场景②④（约束一无法回避）。

#### 优点

- 架构最正：父子组都是真 Raft，与设计稿字面完全一致，无需改设计文档；
- 故障域清晰：端口、term、超时、日志完全隔离，**可观测与排障最友好**；
- 平滑扩展：拓扑扩到 ≥3 机房时，父组天然是真多数派，**降级逻辑可以整体关掉**（退回标准 Raft 安全性）；
- 复用既有选举代码路径（含 PreVote、check-quorum 等成熟机制），而非自研协议。

#### 缺点与风险

- **部署变更**：需新增父组端口（`子组端口 + cross.port.offset`，缺省 22001；防火墙、配置、运维手册全部要改）；
- 每进程 **2 套 transport + 2 套定时器 + 2 份 term/日志**，资源与复杂度接近翻倍；
- **父组仍是 2 节点 Raft**，`majority(2)=2` 的约束依旧成立 → **同样要实现降级**，
  即"真 Raft 的严格性并没有换来实际收益，只换来了复杂度与端口"；
- **席位交接更难**：子组 Leader 切换时，父组节点要经历 活动 ↔ 被动 切换，
  需处理"旧代表还持票/还在重试"的重叠期，否则父组 term 会被无谓推高；
- 两套日志两套存储，持久化目录与恢复流程更复杂。

#### 非功能性

| 维度 | 评估 |
|---|---|
| 可用性 | 高：同上策，满足四场景 |
| 一致性 | 中：分区双主风险同样存在（约束二），与上策等价 |
| 性能 | 中：父组心跳跨机房广播，且两套 transport；但父组日志极小，开销可控 |
| 可扩展性 | **优**：≥3 机房时可关闭降级、回归标准 Raft 多数派 |
| 可观测性 | 优：两组状态完全隔离 |

---

### 6.3 下策 C：机房加权 quorum（单组，伪级联）

> **仅作对照，不满足"实现级联"的诉求。**

#### 结构

把 6 个节点合并为**一个** Raft 组（所有节点互为 peer、跨机房直连），
通过 `VoteWeightStrategy` 实现"主机房优先"：

```
主机房 3 节点权重各 2，备机房 3 节点权重各 1
total = 3*2 + 3*1 = 9，required = 9/2 + 1 = 5

主机房 3 节点全活 = 6 ≥ 5 → 主机房可成主 ✅（主机房优先）
备机房 3 节点       = 3 < 5 → 备机房不可成主 ✅（对侧活着时服从）
主机房全灭，备机房 = 3 < 5 → ❌ 无法成主，场景②失败
```

要让场景②④成立，仍需"把失联机房的节点摘出权重分母"——
在**单组**语义下，这等于**修改集群成员配置（configuration change）**，
而 Raft 成员变更是出了名的难以做对（joint consensus / 单步变更的边界条件）。

#### 优点

- 改动面**最小**：补 P1-P4 即可跑起来，不动 `Speedboat` 结构；
- 单组单日志单 term，概念最少；
- 复用全部既有 Raft 代码与测试。

#### 缺点

- **不是级联**：与设计稿口径直接相悖，`RaftGroup` 的父子组语义仍然空转；
- 场景②④**当前不满足**；要满足就必须做成员变更级别的降级，风险反而最高；
- 6 节点跨 WAN 直连，心跳与日志复制流量是**全互联**（5 条 WAN 链路），性能最差；
- 机房级故障会被判定为"丢了 3 个 follower"，`check-quorum` / PreVote 行为需要重新调参；
- 与已完成的六机验证结论冲突，等于推翻已有架构事实而不解决它。

## 7. 决策记录

> 本节为业务/架构决策的最终结论，实现以本节为准。

### 决策一：实现形态 → **中策 B（父组真 Raft）+ 机房权重**

父组实现为**完整的 Raft 组**，每进程两套 `RaftNode` + 两套 `NettyTransport`
（子组 21001、父组 22001 = 子组端口 + `cross.port.offset`，缺省偏移 1000）。
同时**必须叠加机房权重**——双机房场景下仅靠标准多数派无法表达"主机房优先"。

> ⚠️ **父组不能复用 `DatacenterVoteWeightStrategy`。**
> 该策略按"同机房 +2 / 异地 -1"计算，而父组的两个成员各自看自己都是"同机房"，
> 于是两侧 self 权重都是 3、`required` 都是 2 → **两房都能当选 → 直接违反唯一性硬约束**。
> 父组需要的是**机房优先级权重**（由机房自身属性决定，与"是否同机房"无关），详见 §8.3。

### 决策二：一致性策略 → **CP（硬唯一性）**，推翻原 AP 决定

**新增硬约束：全局 Leader 必须「只有一主或无主」，绝不允许双主。**

这意味着**彻底移除"失联降权 / 降级接管"机制**——降级正是双主的唯一来源。
唯一性由**不对称权重**在数学上保证，而非靠超时判据（超时判据在分区下必然两侧同时触发）。

代价（已接受）：**场景② 退化为"无主"**，主机房整体死亡时备机房无法自动接管。
由此引入**人工升级 API**（§8.6）作为运维兜底手段。

### 决策三：锁 / 数据面 → **D3（本次只做选主级联）**

`LockStateMachine` 行为维持现状（各机房本地处理），仅让 `isMain` 从"每房一个"收敛为"全局唯一"。
锁的跨机房语义后续单独出设计。

### 决策四：父组法定多数 → **按机房聚合分母**（实现期发现，必须修正）

`peerIds` 在 Raft 里同时是**消息投递集合**与**多数派分母的成员集合**，而父组对侧代表
是**运行期才确定**的——为送达未定的代表，peer 必须铺满对侧机房全部节点，于是分母被虚增：
逐节点累加得到 `total=4 / required=3`，主机房 `self=2` 永远不够，**父组连基线都选不出主**。

因此多数派口径改为**按机房聚合**：同一机房的多个 peer 是**同一席位的多条投递路径**，权重只计一次，
`total` 回到 `Σ机房权重`，与 §8.3 的唯一性推导对齐。开关为 `VoteWeightStrategy.quorumByDatacenter()`
（缺省 `false`），仅父组的 `DatacenterPriorityVoteWeightStrategy` 启用，**既有单机房行为逐字节不变**。

同步修正 `HeartbeatWatchdog` 的自身权重硬编码（原为 `1`，会把主机房误降级）。
详见 §8.3.1。

## 8. 选定方案详细设计（中策 B + 不对称权重 + CP + 人工升级）

### 8.1 双层结构

```
┌───────────────────────────────────────────────────────────────┐
│ 父组（跨机房层）                                               │
│ - 端口 = 子组端口 + cross.port.offset（新增，默认 1000）        │
│ - 成员 = 两机房的子组 Leader（代表），共 2 个投票成员            │
│ - 超时 = election.cross.timeout（3000-5000ms）                 │
│ - 无状态机（no-op）、日志上限极小、独立 term / 持久化目录        │
│ - 机房权重（不对称）+ 多数派，禁止降级                          │
└───────────────────────────────────────────────────────────────┘
                              ↑ 代表席位（动态）
┌───────────────────────────────────────────────────────────────┐
│ 子组（机房内层）                                               │
│ - 端口 21001，成员 = 本机房 3 节点                             │
│ - 超时 = election.intra.timeout（150-300ms）                   │
│ - 现有 Raft 逻辑保持不变，补传 voteWeightStrategy              │
└───────────────────────────────────────────────────────────────┘
```

### 8.2 席位规则

- 本进程**仅当** `子组.isLeader()` 时，父组节点进入**活动态**（可竞选、可投票）；
- 否则**被动**：不竞选、不投票（收到父组投票请求回绝——本机房代表会响应）；
- 父组 `RequestVote` 向**对侧机房全部 3 个节点**广播，只有对侧子组 Leader 会以活动态响应，
  天然解决"对侧代表是谁"的发现问题，无需服务发现；
- `isMain` = `子组 Leader && 父组 Leader`；
- 子组 Leader 切换时，父组席位交接需**去抖**（子组 Leader 稳定期超过阈值才接管席位），
  避免父组 term 被无谓推高。

### 8.3 机房权重（不对称，唯一性的数学基础）

**这是整个方案的核心。** 父组权重由**机房自身的优先级**决定，而非"同机房 / 异机房"：

```
父组逻辑成员：H = 主机房代表，B = 备机房代表
权重（可配）：W_main = 2，W_backup = 1

total     = W_main + W_backup = 3
required  = total / 2 + 1      = 2

主机房代表 self = 2 ≥ required(2) → 可单方成主 ✅
备机房代表 self = 1 <  required(2) → 不可单方成主 ✅
```

**唯一性的证明**：双主要求两侧**同时**满足 `self ≥ required`，
即 `W_main ≥ req` **且** `W_backup ≥ req`。由于 `req = (W_main+W_backup)/2 + 1`，
两个权重不可能同时 ≥ 其和的一半加一（除非两者相等，此时各自 = `req - 1`）。
权重不对称 ⇒ 结构上**不可能双主**，与超时、网络状态无关。

#### 8.3.1 分母口径：`peerIds` 的双重身份冲突（实现期发现）

§8.3 把父组当作"2 个投票成员"，但**实现层面 `peerIds` 放不了 2 个**：

- 父组成员是各机房的**子组 Leader**，而对侧代表**运行在哪个进程、由谁当选是运行期才确定的**；
- 为把 RequestVote / AppendEntries 送达对侧**尚未确定的**代表，peer 列表必须铺满**全部进程**
  （见 §6.2「父组为何是全网互联」，六机即 5 个 peer）；
- 但 `peerIds` 在 Raft 里同时是**多数派分母的成员集合**。

两者天然冲突。若仍按节点逐个累加权重：

```
主机房父组节点：self = 2（机房权重），5 个 peer（本机房 2 + 对侧 3）各 1
total    = 1（自身硬编码） + 5×1 = 6
required = 6/2 + 1 = 4
self(2) < 4 → 永远凑不齐多数 → 父组连基线都选不出主，整套级联直接失效
（旧的"只连对侧"拓扑下为 total=4 / required=3，同样 self(2) < 3 不成立）
```

**修正**：法定多数按**机房聚合**——同一机房的多个 peer 视为**同一席位的多条投递路径**，权重只计一次：

```
total    = Σ(机房权重) = W_main + W_backup = 3
required = 3/2 + 1 = 2          ← 回到 §8.3 的原始推导
```

开关挂在 `VoteWeightStrategy.quorumByDatacenter()`（缺省 `false`），只有父组使用的
`DatacenterPriorityVoteWeightStrategy` 返回 `true`，**单机房与既有权重策略的分母计算逐字节不变**。

必须**同口径**修正的位置——否则会出现"选举按权重判多数、看门狗按节点计数判多数"的分裂：

| 位置 | 职责 |
|---|---|
| `QuorumCalculator.totalWeight` | 分母，按机房去重 |
| `QuorumCalculator.receivedWeight` | 已收票，自身按 `selfWeight` 计 + 按机房去重 |
| `QuorumCalculator.grantedWeight` | 预投票票数，同上 |
| `QuorumCalculator.matchedWeight` | 复制多数，同上 |
| `QuorumCalculator.freshWeight`（新增） | check-quorum 新鲜权重，同上 |
| `HeartbeatWatchdog` | 只负责筛出"哪些 peer 新鲜"，权重计算交回 `QuorumCalculator` |

> **`HeartbeatWatchdog` 曾把自身权重硬编码为 `1`**：主机房 `self=2`，杀光备机房后
> `freshWeight(1) < required(2)` 会被**误降级**，场景④退化为无主。这正是两个口径分裂的典型后果。

**配套门控**：预投票应答侧 `doHandlePreVoteRequest` 同样受**代表席位门控**与**机房优先级闸门**约束。
缺了它们，对侧 3 个进程会各应一票、凭空凑成多数，使低优先级机房的探测恒通过、
随后反复进入正式选举抬 `term`（虽因 RequestVote 闸门不会真正当选，但会造成无谓抖动）。

> 依赖关系：预投票探测**不修改** term/持久状态，故闸门无需像 `RequestVote` 那样
> "先对齐 term 再拒绝"（那条顺序是为了让本节点 term 不落后于对侧）。
> 同时 `doStartPreVote` 的"探测超时兜底转正式选举"保证了加门控不伤活性。

### 8.4 各场景行为（硬约束达成情况）

| 场景 | 父组行为 | 全局主数量 |
|---|---|---|
| 正常 | H self 2≥2 当选；B self 1<2 凑不齐 | **1** |
| ① 杀主节点 | 主机房子组内重选，新 Leader 接替父组席位 | **1** |
| **两机房网络分区** | H self 2≥2 成主；B self 1<2 无主 | **1** ✅ |
| ③ 主机房恢复 | term 单调收敛，低 term 方自动退让为 Follower | **1** |
| ④ 杀光备机房 | H self 2≥2 单方成主 | **1** ✅ |
| ② 杀光主机房 | B self 1<2 **无主**，直到人工介入或主机房恢复 | **0** ⚠️ |

> 场景②的"无主"是**刻意设计的结果**，不是缺陷：它是唯一性硬约束在两故障域下的必然代价。
> 运维兜底手段见 §8.6。

### 8.5 禁止降级（关键安全决策）

**父组不得实现任何"失联降权 / 降级接管"逻辑**，理由：

- 降级的判定依据是"对侧失联超时"，而**网络分区与机房全灭在网络层面不可区分**；
- 分区时两侧各自判定对侧失联、各自降权、各自当选 ⇒ **双主**；
- 任何"抖动退避 / 大步 epoch / 只允许一侧降级"都只是**缩小**窗口，无法消除，
  且会让系统处于难以推理的状态。

因此父组分母**固定**为两房代表，`required` 恒定，与可达性无关。

> **PreVote 处置：父组保留 PreVote，不禁用。**
> 标准 PreVote 要求对侧同意才允许升 `term`，在父组两成员且一侧死亡时确实会阻塞**正常**路径；
> 但 `ElectionCoordinator.doStartPreVote` 已实现「探测超时兜底转正式选举」——多数派拒绝或失联
> 超时后自动进入正式选举，**活性不回退**；同时 PreVote 仍能挡住"分区恢复节点以暴涨 `term`
> 打奔现行 leader"的收益，故不禁用。
>
> 与之配套，预投票**应答侧**必须受代表席位门控与机房优先级闸门约束，否则对侧多个进程会
> 各应一票凭空凑成多数（详见 §8.3.1「配套门控」）。

### 8.6 人工升级 API（运维兜底）

场景②下全局无主，需提供**显式的人工介入手段**，把备机房提升为全局 Leader。

#### 语义

- **仅在"无全局主"时允许**（默认拒绝在有主状态下提升，防止误操作直接造成双主）；
- 提升是**显式、可审计、可回退**的运维操作，操作者需自行承担"主机房其实只是分区"的风险；
- 系统自动行为仍保证唯一性；**唯一可能造成双主的是强制人工操作**，这是正确的工程边界。

#### 门面 API（新增静态方法）

| API | 说明 |
|---|---|
| `Speedboat.promoteDatacenter(datacenterId, force, reason)` | 提升指定机房为高优先级。`force=false` 时若当前存在全局主则拒绝 |
| `Speedboat.restoreDefaultPriorities(reason)` | 回退到配置文件中的默认优先级 |
| `Speedboat.getPrioritySnapshot()` | 查询当前生效的机房优先级视图（含来源：配置 / 人工） |

#### 生效机制

1. **持久化**：新的优先级表落盘（与 `term`/`votedFor` 同级持久化，重启不丢）；
2. **term 大步跃升**：提升时父组 term 按固定步长跃升，确保主机房恢复后即便自行发起选举也追不上；
3. **传播**：优先级表随父组心跳/投票消息携带，主机房恢复后以低 term 自动退让为 Follower，
   并从父组心跳学到新优先级表；
4. **锁定**：提升生效后**保持**，主机房恢复**不会自动抢回**，必须显式调用回退 API —— 避免抖动与双主；
5. **幂等**：重复提升同一机房是无害的 no-op；
6. **审计**：以 WARN 级别结构化日志记录 `promote/restore` 的机房、操作者、`force` 取值、`reason`、前后优先级表。

#### 风险提示（须写入 MANUAL）

- 若在主机房**仅网络分区而非死亡**时强制提升，将造成双主——这是该 API 唯一能破坏唯一性的路径；
- 提升后若主机房自行恢复，需运维**先确认**再决定是否调用回退 API，切勿自动化回退；
- 建议在提升前通过带外手段（跳板机 / 控制台）确认主机房进程确已终止。

| V11 | vbox 三机回归 20 断言 | 20/20 | 保持全绿 |

**分区专项（唯一性硬验证）**：用防火墙/iptables 模拟两机房**网络分区**（进程存活、非 kill），
断言全程 `isMain=true` 计数 **≤ 1**，并记录分区期间主机房成主、备机房无主的判定耗时。
这是本次实现**最关键**的验证——唯一性约束必须在分区下成立才算达成。
